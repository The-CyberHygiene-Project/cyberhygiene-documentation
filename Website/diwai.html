About This Reference System

Why a Second Reference System?

Reference System #1 (dc1, cyberinabox.net) proved the underlying research question: an open-source stack, assisted by AI for both construction and empirical NIST 800-171A assessment, can be built and held to live-verified compliance rigor rather than self-attestation alone.

Running dc1 for real also surfaced a clear finding: a full domain-controller architecture (FreeIPA, Kerberos, LDAP, an integrated CA) is over-specified for a system this size — realistically one server and a handful of workstations. DIWAI explores the opposite end of the spectrum: how much of the same control set can be met with one consolidated appliance instead.

What DIWAI Is

  • A single-appliance alternative architecture to RS1's multi-service domain controller
  • A live testbed for AI-assisted system administration with hard technical guardrails
  • An independent system with its own SSP, POA&M, and SPRS score — not a subset or clone of cyberinabox.net
  • Documented as it is built, including findings against its own prior claims

What DIWAI Is NOT

  • A certified or C3PAO-assessed compliant system
  • A turnkey product — see Risks on the main page
  • Dependent on cloud AI services — the AI tooling below is fully offline-capable

Architecture

DIWAI consolidates firewall, domain services, mail, VPN, IDS/IPS, SIEM, and monitoring onto a single Mac mini M4 Pro host, with a FIPS-validated Rocky Linux 9.7 service VM for the Linux-native half of the stack. The Mac mini hardware was repurposed in April 2026 from Reference System #1's original standalone AI server — see the 2026 Update on the main page.

Host (Mac mini M4 Pro)

  • Boundary router and hypervisor
  • FileVault full-disk encryption
  • 389 Directory Server (identity, in place of FreeIPA)
  • Local AI model server (LM Studio)

Rocky Linux 9.7 Service VM

  • FIPS 140-2 cryptographic mode enabled
  • Wazuh SIEM/XDR, Suricata IDS/IPS, auditd
  • Mail (Postfix/Dovecot)
  • CUI document store

Governance

  • Its own independent policy set (DIWAI-*-001 series)
  • Its own SSP and POA&M, versioned separately from RS1
  • No shared or inherited controls across systems, even where co-located

Technical configuration, policies, and the full change-record history are documented in the diwai and Cyberinabox-PhaseIV GitHub repositories.

Local AI Tooling, With Hard Guardrails

DIWAI's AI assistance runs entirely offline through LM Studio as a single local model server — no cloud dependency. The interesting engineering is less the AI itself and more the guardrails placed around what it's allowed to do unsupervised.

Repair Library

A fixed catalog of pre-approved repairs. A repair runs only if the ISSO has approved its exact code using a hardware key (YubiKey, PIN + touch) — showing the planned change, requiring a typed confirmation, keeping a backup, and supporting undo. Any code change invalidates the approval; re-approval is required after every reinstall.

Aider, On a Leash

The coding-assistant tool used to draft configuration changes runs through a launcher that refuses project-level settings capable of running code without approval. A model-proposed command never executes without a typed "yes" — verified live across 8 of 8 adversarial checks, including a planted "ignore your instructions" prompt that was ignored 3 for 3.

Verification, Not Just Claims

The October 2026 build of this tooling was tested, not just asserted: 325 automated tests passing, test-first (each test observed to fail before the fix was written), and an independent code review before install that found 1 critical and 7 important findings — all fixed, each with its own failing-first test. The critical finding: an early version of undo would have accepted any folder as a valid "run," which could have let an approved repair's undo write unapproved content with no typed confirmation. It was fixed before release.

This project has also turned the same scrutiny on its own prior work: a documented verification sweep of earlier POA&M closures found several that had been marked resolved on the strength of evidence that didn't actually support the conclusion — the same class of defect the assessment exists to catch in general. Those findings were corrected in the record, not quietly dropped.

Risks

The same cautions on the main project page apply here, plus one specific to AI tooling

  • A single appliance is also a single point of failure — the host is simultaneously boundary router, hypervisor, and CUI document store
  • Guardrails reduce risk, they don't eliminate it — the repair library's own pre-release review found a critical defect; later ones may exist
  • Self-assessment is not certification — 100/110 is this project's own number, not a C3PAO's
  • AI drafting still needs expert review — in testing, AI-drafted compliance text consistently failed to cite a fitting assessment objective without human review
