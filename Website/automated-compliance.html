What "Automated Compliance" Means Here

Not What It Might Sound Like

This is not a claim that AI can certify a system compliant, or that automation replaces assessment. The whole rest of this website argues against exactly that idea — see Risks and the 2026 Update on the main page, where a credited control turned out to have quietly stopped existing.

The actual research question is narrower: can AI-assisted tooling make continuous re-verification cheap enough that it actually happens, instead of compliance evidence going stale between the occasional, expensive, manual reassessment?

This work, proven out on DIWAI, is also Step 2 of the collaborative Cyber Appliance Project with Jeff — the plan there is to replicate it onto new hardware as a dedicated automated compliance engine, not just document it after the fact.

The Working Hypothesis

  • Most compliance failures in this project's own history weren't exotic — they were claims that went unverified after the system around them changed
  • A monitor that only checks "is the service running" misses the failure modes that actually matter — see Case Studies
  • AI can help write and run verification checks faster than a human alone, but AI-drafted conclusions still need the same skepticism as human-drafted ones
  • The real test of a monitoring/assessment tool is whether it can be falsified — including when it's checking itself

How It Works

Three separate components, deliberately kept separate so that detecting a problem, deciding what to do about it, and actually doing it are three distinct steps — not one opaque action.

1. Control-Health Monitor

Continuously checks control state and writes a JSON report. Originally just process/service checks — "is it running" — until a real incident (see Case Studies) proved that isn't the same question as "is it working."

2. diwai-diagnose

Reads the control-health monitor's report and names the specific, pre-approved repair that applies — but is strictly read-only. It diagnoses; it never runs anything.

3. diwai-repair

Executes a repair from a fixed catalog, and only if the ISSO has approved that repair's exact code with a hardware key (YubiKey, PIN + touch) — shows the planned change, requires a typed confirmation, keeps a backup, and supports undo. Any code change invalidates the approval.

Why Three Steps, Not One

Collapsing "detect, decide, act" into a single automated action is exactly the kind of system that produces convincing-looking results with subtle, unreviewed errors — the same AI Competency Paradox this project flags elsewhere. Keeping diagnosis read-only and gating execution behind a human with a physical key means a wrong diagnosis is just a wrong report, not a wrong change to a production system.

Case Studies: Where This Already Caught Something

Both of these are documented against this project's own prior work, not a hypothetical. That's deliberate — a monitoring effort that only ever reports good news isn't demonstrating anything.

"Running" Is Not "Working"

On 2026-08-03, the control-health monitor's 24 checks all reported healthy throughout a real, six-minute production incident in which the web server process (httpd) was active — but every authenticated request it handled returned HTTP 500. A process-liveness check cannot see that. The monitor was correctly reporting a fact; it was simply the wrong fact for the question "is this control working."

Fixed the next day: an authenticated probe was added and negative-tested — confirmed to actually fail when the real condition is reproduced, not just assumed to work. The check count went from 24 to 25. The fix is small; the lesson generalizes: a monitor's blind spots are discovered by real incidents, not designed away in advance.

Auditing the Auditor

A dedicated verification sweep re-examined 38 prior POA&M closures against this system's own register. The finding: only 1 of 38 recorded both a positive and a negative test; 7 said "verified" with no stated mechanism; 3 rested on a document alone; and 22 of 38 stated no evidence whatsoever. The register, as written, could not distinguish a tested closure from an assumed one.

Six closures were re-tested live. All six held — but the sweep also found three previously credited points were unsupported: a remediation had been verified on the service VM, then credited as covering the Mac host too, when the Mac host was never touched. Those points were flagged DISPUTED pending an explicit owner decision, rather than quietly left credited.

The resulting practice rule, stated directly in the record: "A closure must state the evidence that would have falsified it." One sentence, applied going forward, intended to make a sweep like this unnecessary the next time.

Limitations

What this approach does not solve

  • AI-drafted compliance text still needs expert review — in testing, six out of six AI-drafted policy/documentation changes failed to cite a fitting NIST 800-171A assessment objective without a human catching it
  • Monitoring blind spots are discovered, not eliminated — the "running vs. working" gap above was found by a real outage; there is no reason to assume today's check list has no equivalent gap left
  • Automation can scale a mistake as easily as a correct check — a monitor that quietly checks the wrong thing produces false confidence faster than a human checking by hand would
  • This is one system's internal tooling, not a validated product — see the main project's Risks section for the general caveats that apply here too
